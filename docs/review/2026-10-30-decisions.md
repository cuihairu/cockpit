## 先学会分辨阻塞，再决定花什么成本

- **缺环境**：代码可能已经写好，但还没有在真实设备上证明可用。正确投入通常是借设备、安排验收窗口，而不是继续补代码。
- **缺决策**：要确定服务谁、解决什么问题、允许花多少钱、出了问题如何退回。先把一个小范围说清楚，再立项。
- **已决定暂缓**：当前没有充分收益或前置条件未满足。维持暂缓也是有效决策，不必每次巡检重新讨论。
- **已有部分成果**：模拟测试能证明“程序按约定处理输入”，不能证明“真实厂商或硬件一定按这个约定响应”。完成开发、完成验收、适合生产是三件事。

建议的总体顺序：先复用现有设备、账号做高价值验收；新开发优先补 Agent 可靠性和权限边界；多云和 OOB 沿已批准路线收口；高级调度、协作和新硬件适配按真实需求触发。新开发与验收各保持少量在办事项，避免所有条目同时争抢设备和注意力。

成本以低/中/高作相对比较，指新增工作、设备和维护负担，不是报价或工期承诺。不假设你已经拥有某账号，也不替你批准采购、生产暴露或付费资源。

## 一、真机、真实账号和凭据：15 项

### 01｜service-health 生产接入

来源：`todo.md:19`。缺口：可用生产 WebSocket 地址，或明确的局域网入口授权。

**推荐决策：优先核对并复用受控的加密代理入口；保持服务监听回环地址。仅在代理路径不适用时，单独评估限定来源的 LAN 暴露。**

理由：

- **成本低**：先确认现有入口能否转发 WebSocket，通常比迁移监听地址、调整多处防火墙影响面小。
- **收益直接**：恢复 VM 的健康上报，已有 agent 和探针才能发挥作用。
- **风险可控**：只知道域名能打开网页，不等于 agent 的 WebSocket 路径、认证和持续连接都正常。
- **决策思路**：选能解决实际连通问题、又增加最少新入口的方案，不能把“开放端口”当作默认解法。

**立即执行动作：** 用户或部署负责人给出完整候选 `wss://…` 地址、认证方式和允许接入的 VM；随后核对代理路径及证书，约定连接成功与心跳出现的验收标准，再由获授权人员改 `SERVER_URL`、启用服务，保留原配置以便退回。

**明确不做/延后：** 本次不启用 agent、不改生产监听；不直接开放全网 `:9000`；没有有效入口前不靠反复重启碰运气。

### 02｜Windows SCM 服务管理

来源：`todo.md:22`。缺口：真正提权的管理员 agent 会话，已有两台非提权机器的校验层证据。

**推荐决策：安排一次限定时段的管理员验收，使用可删除的测试服务；保留已经通过的非提权证据。**

理由：

- **成本低至中**：主要成本是管理员配合和测试窗口，继续在普通会话重跑收益很低。
- **收益明确**：补上列表、启停、自启切换和超时路径，而不是重复证明“权限不够”。
- **风险真实**：启停生产服务会影响业务；测试服务能把影响限制在可恢复范围。
- **决策思路**：管理员组成员身份不等于当前进程已经提权；验收应核对实际执行身份。

**立即执行动作：** 由主机负责人提供已提权的验收会话，确定测试服务、初始状态及清理方法，按 `acceptance-checklist.md` 对应 SCM 条目逐项留证，结束后还原。

**明确不做/延后：** 不关闭 UAC、不索要管理员明文密码、不碰系统关键服务；连接层完成前不把整项标为通过。

### 03｜macOS launchd 服务管理

来源：`todo.md:27`。缺口：macOS 真机及系统域操作所需权限。

**推荐决策：优先借用现有 Mac 做一次集中验收，先校验层、再临时 LaunchDaemon 执行层；暂不为这一项单独采购。**

理由：

- **成本中**：借机和安排权限比购买专机更轻；交叉编译准备已完成。
- **收益可复用**：同一台 Mac 未来还能服务 iOS 验收，但两项完成条件不同。
- **风险可隔离**：自建临时任务可以验证启停与回退，不影响 macOS 系统服务。
- **决策思路**：编译通过只证明代码可生成，不证明 `launchctl` 的实际权限和运行行为。

**立即执行动作：** 收集可借 Mac 的系统版本、可用窗口和管理员操作方式，准备临时 plist 的安装/还原步骤；由机主按已有 launchd 探针及清单验收。

**明确不做/延后：** 不把 Linux 模拟或 CI 编译算作真机通过；没有持续 macOS 需求前延后采购和额外平台扩展。

### 04｜NAS 多平台及存储演练

来源：`todo.md:30`。缺口：DSM 6/7、TrueNAS CORE/SCALE、OMV 等真实环境与账号。

**推荐决策：先验实际在用的一种 NAS，再分批扩大覆盖；API 读取与磁盘故障演练分开进行。**

理由：

- **成本高且分散**：一次凑齐所有系统、版本和存储形态，会明显增加设备和维护成本。
- **收益按使用量排序**：先证明你每天依赖的设备可用，比同时宣称兼容多个平台更有价值。
- **风险差异大**：查看 API 与人为制造 mdadm 降级不是同一风险等级，后者必须用可丢弃的数据和磁盘。
- **决策思路**：一台设备通过只能覆盖对应平台、版本和场景，不能自动推及整张清单。

**立即执行动作：** 盘点已有 NAS 型号/系统版本、可提供的只读账号及测试存储，选首个平台按清单验收；为 mdadm/ZFS/SMB/NFS 分别标注所需独立环境，故障演练单列恢复方案。

**明确不做/延后：** 不在存有重要数据的阵列上拔盘或造故障；未提供的其余平台继续标阻塞，不因首个平台通过而勾整条。

### 05｜备份云远端 S3/B2 完整链

来源：`todo.md:32`。缺口：真实 S3/B2 凭据及 server 宿主上的 rclone。

**推荐决策：先用已有的一家真实对象存储完成上传、下载、恢复和内容校验，再补另一家的差异验收。**

理由：

- **成本中**：需要存储、流量及宿主软件准备；复用已有账号能减少开户与维护负担。
- **收益高**：只有能从远端恢复，备份才真正减少数据丢失风险。
- **风险可限制**：独立测试桶或目录、有限权限和费用上限可降低误删及意外开销。
- **决策思路**：上传成功不是备份闭环；要用恢复后的文件证明内容完整，并覆盖 GB 级与限速。

**立即执行动作：** 确定首家供应商、测试桶/前缀、费用上限和清理日期，通过现有安全渠道配置凭据；获授权人员确认宿主 rclone 后，先小文件、再 GB 级数据，恢复至空目录并校验内容。

**明确不做/延后：** 不把本地兼容服务当作真实 S3/B2 通过；不操作生产备份目录；第二家未验前保留该部分缺口。

### 06｜录制异地 rclone 推送

来源：`todo.md:34`。缺口：真实 rclone 远端配置。

**推荐决策：复用第 05 项的远端基础设施，但使用独立目录、权限和保留规则。**

理由：

- **成本低**：同一套远端接入能解锁两项验收，减少重复配置。
- **收益直接**：设备损坏后仍有录制可追查；也能验证回放文件是否完整。
- **风险不同**：会话录制可能包含操作内容，不能机械套用普通备份的读权限和保存期限。
- **决策思路**：基础设施可以共享，数据的访问和保留责任需要分别决定。

**立即执行动作：** 指定录制专用前缀、谁能读取、保留多久；由负责人配置真实 remote，用无敏感内容的短录制验证推送、取回、回放及失败留痕，按清单覆盖清理行为。

**明确不做/延后：** 不上传真实敏感会话试功能；不公开桶、不无限期保存；本次不安装 rclone 或写入配置。

### 07｜ACME 签发、续期和浏览器信任链

来源：`todo.md:36`。缺口：真实 ACME 账号与 DNS 凭据。

**推荐决策：使用专用测试域名，先完成 staging 全链，再做 production 签发与浏览器信任验证；续期单独保留证据。**

理由：

- **成本中**：需要域名权限、部署目标和连续验证窗口，单次拿到证书不足以收口。
- **收益高**：同时证明签发、部署、服务读取新证书和客户端信任，减少“证书有了但网站仍报错”的情况。
- **风险可分层**：先在测试环境排除配置问题，降低影响现有 HTTPS 服务的概率。
- **决策思路**：staging 用于练流程，不能据此宣称生产信任链通过；自动续期也不能靠一次手动签发代替。

**立即执行动作：** 指定测试域名、DNS 区域、可操作凭据范围及部署目标；依清单排 staging→production→部署→浏览器链路，另安排续期触发/调度验证和回退证书。

**明确不做/延后：** 不直接替换主站证书试错；不把密钥放进报告或仓库；续期未验前保留该子项。

### 08｜Cloudflare DDNS 与家庭出口多源

来源：`todo.md:38`。缺口：真实 token 和家庭侧出口环境。

**推荐决策：只针对专用测试记录验收，必须在家庭侧 agent 所在网络验证出口判断。**

理由：

- **成本低**：已有家庭网络和账号时，只需准备测试记录及受限凭据。
- **收益明确**：证明更新的确是家庭出口地址，而不是开发机或服务器的出口。
- **风险可限制**：误改记录可能中断访问；测试子域名能隔离影响。
- **决策思路**：同一段代码在不同网络位置观察到的结果可能不同，环境位置也是验收条件。

**立即执行动作：** 给出测试区域/记录名、家庭 agent 和 IPv4/IPv6 目标，通过安全配置提供限区 token；检查多来源结果与错误处理，再验证记录实际更新。

**明确不做/延后：** 不改主域名和生产解析；不拿服务器出口冒充家庭出口；token 未到位不反复运行假验收。

### 09｜overlay：ZT/TS 真授权及双机观测

来源：`todo.md:40`。缺口：ZeroTier/Tailscale 真实凭据和第二台主机。

**推荐决策：先验证目前实际使用的一套 overlay，再补另一套；使用隔离测试网络和两台非关键主机。**

理由：

- **成本中**：需要两个真实节点和管理面权限，单机模拟不能覆盖跨机合并观测。
- **收益高**：验证加入、离开、授权、除名及本机服务状态是否一致。
- **风险需预防**：对当前远程登录依赖的网络执行 leave，可能让验收者失去连接。
- **决策思路**：控制链路要有独立退路，不能依赖正在被测试和切断的那条链路。

**立即执行动作：** 确定首套平台、测试网络、两台主机和独立管理入口；分别准备 ZT/TS 所需凭据，按清单验证控制面与双机状态，结束后移除测试节点。

**明确不做/延后：** 不自研 mesh 数据面；不除名现网节点；仅验一家不代表两家完成，另一家继续保留缺口。

### 10｜SMART 属性表与 FAILED 翻转

来源：`todo.md:42`。缺口：能提供真实 SMART 属性表的磁盘及失败状态证据。

**推荐决策：先在可读 SMART 的实盘完成健康读数；失败链优先使用已故障的报废盘，无该设备就保留失败场景阻塞。**

理由：

- **成本低至中**：借现有直通磁盘比专门造一块坏盘更合理。
- **收益具体**：区分“磁盘健康”“接口不支持”“没有权限”，防止错误乐观展示。
- **风险很不对称**：为了验证告警而损伤健康磁盘，损失远大于获得的测试证据。
- **决策思路**：模拟失败可以验证程序分支，但应与“真实设备 FAILED 端到端通过”分开记账。

**立即执行动作：** 由设备负责人确认接口能透传 SMART、提供脱敏属性表及权限条件；如有已故障测试盘，再按清单验证告警/页面翻转，否则明确登记剩余缺口。

**明确不做/延后：** 不人为损坏健康盘、不对生产盘做破坏性压力测试；不把合成输出算作真实 FAILED 验收。

### 11｜DNSPod/阿里云 DNS、台账与迁移

来源：`todo.md:44`。缺口：两家真实 DNS 账号。

**推荐决策：用测试子域名依次完成单厂商记录操作，再在隔离域完成跨厂商迁移；不迁移生产主域名。**

理由：

- **成本中**：两家账号和解析配置的准备成本大于单接口测试，适合分步收口。
- **收益广**：可同时验证 SRV、TTL 边界、台账联动及迁移后的实际解析。
- **风险隐蔽**：API 返回成功不代表外部解析已更新，缓存和委派同样影响结果。
- **决策思路**：把“控制台/台账已改”与“外部用户能正确解析”分别验证。

**立即执行动作：** 确定测试区域、两家受限凭据、预期 SRV 内容及迁移回退记录；按各账号实际响应核实 TTL 行为，再逐步验台账和迁移解析。

**明确不做/延后：** 不凭记忆硬写所有厂商的 TTL 下限；不动邮件等关键记录；单厂商通过后不提前勾掉跨 provider 迁移。

### 12｜Guacamole RDP 音频

来源：`todo.md:46`。缺口：可用的 Windows RDP 音频环境。

**推荐决策：复用第 02 项的 Windows 主机安排一次 RDP 音频验收，但分别核对 RDP 登录、音频重定向和编码条件。**

理由：

- **成本低至中**：共享设备能减少借机成本，但管理员会话不自动等于可用 RDP 环境。
- **收益明确**：验证声音实际经过现有 Guacamole 链路，静音按钮才有实际意义。
- **风险易误判**：听不到声音也可能是目标机策略或浏览器播放限制，未必是编解码错误。
- **决策思路**：分段确认音源、协商格式、传输和播放，才能知道该修哪一层。

**立即执行动作：** 由负责人确认 RDP 可连接、测试音源可播放，记录协商的 mimetype 及 L8/L16 行为，再验播放和静音，使用无敏感内容的声音样本。

**明确不做/延后：** 不重写桌面协议或增加新远控协议；不为“没有声音”直接改编码；设备缺失时延后真机结论。

### 13｜Android release、签名升级、生物识别、ntfy、SSH

来源：`todo.md:48`。缺口：Android 真机、受控签名材料及 ntfy 配置。

**推荐决策：先借一台实际目标 Android 设备完成正式构建的使用闭环；签名升级单独按同一签名链验证。**

理由：

- **成本中**：借机容易，正确管理签名和升级样本更需要负责人配合。
- **收益高**：覆盖安装、启动、混淆后行为、生物识别、通知和终端这些用户直接感知的功能。
- **风险长期存在**：测试升级若混用签名，会把“安装成功”误当作“原用户可无损升级”。
- **决策思路**：首次安装与原地升级是两条不同路径，模拟器和 debug 构建也不能替代 release 真机验证。

**立即执行动作：** 确定设备/系统版本、签名保管人、旧版与候选版构建以及 ntfy 测试主题；先保留测试数据，再验原地升级、通知、锁定/解锁和 SSH 终端操作。

**明确不做/延后：** 不生成替代正式密钥来冒充升级成功；不把私钥或口令交到报告；首台通过后再按实际用户设备补覆盖矩阵。

### 14｜web 移动端与 Workbench 触屏

来源：`todo.md:50`。缺口：真实触屏设备；todo 已记载基础适配完成。

**推荐决策：借第 13 项设备优先做浏览器触屏验收，另补实际会使用的平板/其他浏览器；只针对可复现问题安排修复。**

理由：

- **成本低**：复用手机，无需先新增开发项目。
- **收益直接**：滚动、拖拽、长按、虚拟键盘遮挡等问题最影响真实操作。
- **风险在交互层**：桌面缩小窗口可以验证布局，却不能完整模拟手指和软键盘。
- **决策思路**：已有自动测试很多时，应补最缺的真实输入证据，而不是继续堆相同类型测试。

**立即执行动作：** 固定一条实际操作路径，覆盖导航、表格横向滚动、Workbench 拖拽/选择、终端输入、横竖屏与软键盘；由持机人记录设备、浏览器及失败步骤。

**明确不做/延后：** 不先重构响应式布局、不替换 UI 框架；不把桌面浏览器设备模式当真机通过。

### 15｜iOS 签名与装机

来源：`todo.md:52`。缺口：Mac、签名所需账号/配置及安装设备。

**推荐决策：保持低优先级；有明确 iPhone 使用者和分发目标后，再准备对应签名与真机环境。**

理由：

- **成本中至高**：除设备外，还有签名、分发和持续维护负担，应由真实需求承担。
- **收益有条件**：没有实际 iOS 用户时，装机成功对当前主要流程帮助有限。
- **风险是长期承诺**：一次装机以后还要维护后续升级，不能只看首次投入。
- **决策思路**：先决定给谁用、如何交付，再核对适合该方式的账号条件，避免为不确定用途采购。

**立即执行动作：** 记录首位使用者、目标机型、测试安装或正式分发方式；若可借 Mac 则与第 03 项合并排窗口，并由负责人核对相应签名条件。

**明确不做/延后：** 当前不建议专门购买 Mac 或开通付费服务；不把 CI 编译当装机通过；本报告不作 Apple 现行费用或分发规则判断。

## 二、功能范围与既有暂缓：4 项

### 16｜防火墙写操作

来源：`todo.md:57`，`docs/guide/decision-log.md` 的 D-2026-10-07-3。

**推荐决策：维持暂缓，先补齐只读真机验收，再基于明确场景重新评估写能力。**

理由：

- **成本高**：写规则不只是“多一个按钮”，还涉及回退、规则归属和失联恢复。
- **收益目前未证实**：只读观察尚有验收前置缺口，新增写能力不会替它完成验收。
- **风险高**：规则错误可能切断管理入口，远程修复也会同时失效。
- **决策思路**：权限越大，越要先证明观察准确、失败能恢复，不能因已有部分基础就跳过前置。

**立即执行动作：** 确定待补的只读目标机与验收条目；未来收集一个具体写规则场景、独立管理入口及自动回退要求，满足前置后再给出小范围立项方案。

**明确不做/延后：** 不开发通用规则增删、不重开已搁置决定；OpenWrt 已批准的限时兜底转发按其独立边界执行，不外推为通用主机防火墙授权。

### 17｜workflow 并行分支

来源：`todo.md:59`，`docs/guide/workflow-design.md` 的 W4/G3。

**推荐决策：继续串行执行已有依赖结构，出现可量化等待成本的真实并行流程后再立项。**

理由：

- **成本中至高**：并行要解决共享资源冲突、取消、失败合并和并发上限。
- **收益有前提**：只有可独立执行且耗时明显的步骤，并行才会显著缩短总等待。
- **风险易低估**：备份、升级、重启同时运行可能互相破坏，速度变快不代表结果正确。
- **决策思路**：先找真实瓶颈；能画依赖图不等于需要并发执行。

**立即执行动作：** 收集一条实际 workflow 的步骤耗时、依赖和共享资源；只有确实存在独立慢步骤、且节省的等待值得维护成本时，才提出限并发设计。

**明确不做/延后：** 不重做 DAG、不实现通用并行调度；不新增已明确不做的 workflow SSE。

### 18｜persona vault 切换硬验收

来源：`todo.md:61`，`docs/guide/persona-vault-mapping.md`。

**推荐决策：保留 local 为当前可用方案；拿到隔离 persona 服务后再做切换验收，按只读 provider 的真实能力定义成功。**

理由：

- **成本低至中**：主要缺服务地址和凭据，重复单测不能替代外部接口验证。
- **收益明确**：验证真实认证、会话锁定及切换后 local 存量是否仍可用。
- **风险是能力误认**：persona 当前映射只读，不支持写删；接口返回不支持不能简单当成回归缺陷。
- **决策思路**：替代后端前先比较能力边界，再验证数据可回退，而不是只看“连通成功”。

**立即执行动作：** 用户提供测试服务地址、凭据引用和无敏感测试条目；验 local→persona→local 及失效/锁定行为，保存不含秘密的结果。

**明确不做/延后：** 不迁移全部生产凭据、不删除 local 存量；不替 persona 新造写删接口、不把缺地址理解为要重写 vault。

### 19｜Jenkins/external endpoint 凭据引用

来源：`todo.md:63`。

**推荐决策：随真实链接功能一同立项，不单独开发凭据引用外壳。**

理由：

- **成本中**：缺具体消费者时，账号类型和授权流程都容易猜错并返工。
- **收益依赖主功能**：单独存入一个凭据并不能让用户完成外部任务。
- **风险需看目标**：普通跳转链接通常无需读取秘密；服务端代调接口才需要设计凭据传递。
- **决策思路**：先明确谁调用谁，再决定秘密是否需要进入这条链路。

**立即执行动作：** 收集首个外部系统、一次具体操作、调用位置和成功标准；链接立项后，只为该场景复用既有 vault，并设计目标限制、权限及脱敏。

**明确不做/延后：** 不建通用任意地址凭据代发器；不在链接 URL 中拼接秘密；没有链接需求前保持暂缓。

## 三、多云：3 项

### 20｜P0 云账号、发现、生命周期、成本地基与 Quota

来源：`todo.md:75`；设计 `docs/design/cloud-provider.md`；当前实例台账路由 `internal/server/api_cloud.go`。

**推荐决策：沿已批准的阿里云+腾讯云收口，先拿真实账号核对只读契约，再验隔离资源生命周期；不扩厂商，也不把已有适配器重做一遍。**

理由：

- **成本中**：两个适配器及账号/存储基础已落，主要新增成本在真实契约、接线、费用和验收。
- **收益高**：真实发现→创建→状态→停止/释放→成本归属，才能证明平台真正控制了云资源。
- **风险有账单后果**：停止不一定消除全部费用；配额、资源状态和计费状态不能靠模拟响应推定。
- **决策思路**：一家的全链比两家的半链更能揭露问题，但双厂商条目必须两家都有证据才能完成。

**立即执行动作：** 分别确定两家测试子账号、区域、资源规格、费用硬上限和清理负责人，经 vault 配置 AccessKey；先只读核对发现/Quota 的原始响应与所需权限。再盘点厂商发现、生命周期 API 与界面仍缺的接线；凭据和付费边界明确后逐家运行最小生命周期，并核对资源清理及剩余计费。成本先明确预计/估算/实际的来源，不用估算冒充账单。

**明确不做/延后：** 不重新申请 P0 立项；不凭空实现 Quota 契约；不把只读数据库实例列表当自动发现完成；不添加第三家、不提前进入 P1/P2；既有全量门禁未绿仍如实保留，不用定向通过替代。

### 21｜P1 资源池、Reconciler、云网络、预算与控制权

来源：`todo.md:78`，多云评审中“避免双重控制”约束。

**推荐决策：先确定“一个资源在同一时刻只有一个写入负责人”，P0 闭环后只挑一个小资源池试点；预算先限制新建、告警和审批。**

理由：

- **成本高**：自动协调器会持续运行，错误不止发生一次，测试和运维责任更重。
- **收益有条件**：资源池确有反复补容量的需求时，自动协调才比人工操作划算。
- **风险核心是争抢**：OpenTofu 与 Cockpit 都写同一资源，可能互相撤销对方动作，产生停机或费用循环。
- **决策思路**：先明确谁有权改，再讨论如何自动改；花费超限首先阻止新增支出，不默认关闭生产。

**立即执行动作：** 在方案中列资源归属：OpenTofu 管的资源由其执行变更，Cockpit 观察或提交计划；Cockpit 独占管理的试验资源才允许 Reconciler 写；外部归属默认只读。列出所有权交接、暂停开关、冲突拒绝和审计条件，待 P0 完成后再确认试点的期望容量及预算。

**明确不做/延后：** 不让两个控制器直接改同一资源；不一次铺开云网络全家桶、不做 CRD 全量模型；预算告警不自动关生产，未完成 P0 不排 P1 实现。

### 22｜P2 智能调度、成本优化、控制面高可用

来源：`todo.md:80`。

**推荐决策：保持未立项，拆成三类需求分别触发，不整包提前建设。**

理由：

- **成本高**：调度、优化和多实例恢复是三类复杂系统，叠加会显著增加维护负担。
- **收益需要数据**：没有真实成本与容量记录，所谓优化很容易优化错目标。
- **风险要匹配损失**：高可用需要一致性、主从和任务恢复设计，不能简单多启动一个 server。
- **决策思路**：先问“当前停机或浪费造成多少实际损失”，再比较解决它的长期成本。

**立即执行动作：** 先记录资源选择耗时、可避免费用、允许停机时间和可接受数据损失；某一项损失足够明确后，仅为该问题提出方案与验收指标，P0 成本数据不足时不下优化结论。

**明确不做/延后：** 不训练智能调度、不自动跨云搬生产、不为名义高可用改数据库或多活部署；P1 没有稳定数据前延后整包能力。

## 四、Agent 强化：3 项

### 23｜P0 Capability、调度隔离、升级回滚、任务可靠性

来源：`todo.md:92`，`docs/review/competitor-landscape-2026-10-20.md`。

**推荐决策：建议批准四个有依赖的独立小范围：Capability 契约→并发/超时隔离→幂等与执行窗口→升级回滚。先把重复执行规则定清，再开启自动重试。**

理由：

- **成本中至高但可分期**：每片都有独立收益，避免一次改动所有 Agent 核心路径。
- **收益覆盖面广**：云、OOB、服务管理等都依赖 Agent，可靠性改进会惠及现有功能。
- **风险在旧节点兼容**：能力字段升级后，旧 agent 不能被误认支持新动作；升级失败也不能把远程入口一起丢掉。
- **决策思路**：操作超时仅表示“没收到结果”，不证明“目标没执行”；重试前必须识别同一个任务。

**立即执行动作：** 先盘点现有 capability 上报与消费位置，为能力/版本/权限状态补最小契约设计；随后分别列并发上限、取消与超时预算、任务身份和重复执行策略、维护窗口，以及升级产物验证、健康检查和回退成功条件。各片立项后按设计→测试→小范围验收推进。

**明确不做/延后：** 不推翻现有 Agent Core 三层结构、不另造插件大框架；不默认重试任意 shell 命令、不直接批量升级全部设备。这里是推荐新拍板，不表示本次授权了实现。

### 24｜P0 短期凭据、资源级权限与轻量模式

来源：`todo.md:94`。这条混合了访问安全与低配运行两个目标。

**推荐决策：拆开排期。先做资源归属和权限矩阵设计；有多人访问时优先落资源级限制及凭据撤销/过期。轻量模式先测目标设备资源，再决定最小构建。**

理由：

- **成本中至高**：权限影响每条 API；轻量模式影响打包与功能组合，合并实施难定位问题。
- **收益按场景变化**：多人共用时，隔离“谁能改哪台机器”价值高；个人使用时不必直接复制复杂访问平台。
- **风险在伪隔离**：token 有效期短，并不自动限制可操作资源；只隐藏菜单也不是权限校验。
- **决策思路**：安全先证明拒绝越权；轻量先测内存、CPU、磁盘和恢复行为，再谈裁剪多少功能。

**立即执行动作：** 明确个人/团队使用方式，画“角色×资源×动作”矩阵，选择最敏感的一类动作作为试点，并列过期/撤销和已有长期凭据迁移规则；为 OpenWrt 等目标给出资源预算并采集基线，据测量结果选是否需要最小构建。

**明确不做/延后：** 不另造完整证书基础设施、不因短期 token 省略资源检查；不先分叉两套 agent。单人环境的全面行隔离与没有资源瓶颈的激进裁剪延后。

### 25｜P1 离线缓冲、会话共享、统一电源、源码深读

来源：`todo.md:96`。旧竞品评审的“WoL 未做”已被后续 OOB 实现覆盖。

**推荐决策：不要整包立项；P0 后按实际断线损失优先评估离线缓冲，其余分别按需求触发，统一电源只做已有能力的归并。**

理由：

- **成本差异大**：缓冲是数据可靠性，会话共享是多人授权，四套源码深读是研究，不适合共用一个完成标准。
- **收益需能落地**：经常丢监测数据时缓冲有价值；没有双人远程协作时共享收益较小。
- **风险需分别管**：离线缓冲有磁盘耗尽和重复补报风险，共享会话有操作归属与秘密暴露风险。
- **决策思路**：借鉴开源应为一个具体问题服务；已有 WoL/云操作不必再写第二套。

**立即执行动作：** 记录断线时长及数据缺口，给离线缓冲写出容量、过期、去重和补报顺序；为共享记录一个双人场景及只看/可操作边界；盘点 WoL/PVE/云电源现有接口；源码阅读只选择当前设计问题对应的项目和章节。

**明确不做/延后：** 不一口气做四套研究报告、不重写电源 provider；不缓存离线任意写命令并在重连后自动执行；无协作需求时延后会话共享。

## 五、OOB 与虚拟化：3 项

### 26｜P0 OOB 与 OpenWrt 自启动验收

来源：`todo.md:108`，`docs/design/oob-openwrt-bootstrap.md`。

**推荐决策：沿已批准方案收口，优先借一台可恢复的 OpenWrt 真机验断电/进程异常恢复，同时验证兜底通路的实际可用边界。**

理由：

- **成本中**：框架、发现、WOL、探活、转发和页面已有成果，最大新增价值来自真机而非再写包装代码。
- **收益关键**：兜底节点如果断电后不能自行回来，最需要救援时就失去意义。
- **风险在真实系统契约**：procd 有脚本不等于无限次稳定恢复；ubus 写规则也尚需匹配实际固件。
- **决策思路**：识别到 AMT/DASH/Redfish 服务，不等于已经验证认证、电源或 KVM；每种能力要有自己的证据。

**立即执行动作：** 由设备负责人给出型号、固件、架构、配置备份、独立管理入口和断电测试窗口；按清单验断电重启、进程退出后的重启、重复失败、网络晚就绪与恢复后的连接。结合现有 retry=5 等参数观察行为，不先承诺无限恢复；再验 WOL、真实 ubus 转发、到期规则清理，并检查 server 不可达时本地还能使用哪些兜底路径。

**明确不做/延后：** 不给整个现网网关随意断电、不扩大到主机防火墙通用写；不把定时手动清扫接口当成已证明自动到期清理；不宣称所有硬件能力完成，AMT/DASH/Redfish 认证及操作面仍随真机凭据片验收，不新增 mesh 数据面。

### 27｜P1 机型矩阵、Snapdragon Guardian、IP-KVM

来源：`todo.md:113`，OOB 评审的逐型号实测要求。

**推荐决策：矩阵作为每次 P0 验收的同步记录，不必等全部 P0 完成；Guardian 仅保留研究，IP-KVM 等真实救援缺口出现后再评估。**

理由：

- **成本低到高不等**：记录已测事实成本低，购买新平台和外置 KVM 成本明显更高。
- **收益在可信边界**：用户知道某型号、固件和网络条件下哪些能力可用，比“支持某 CPU 品牌”更有帮助。
- **风险在泛化**：同一系列不同固件、授权和配置可能能力不同，不能凭宣传资料填支持矩阵。
- **决策思路**：把兼容证据与未来候选清单分开；只有已有方案救不了的场景才值得新增硬件路线。

**立即执行动作：** 在后续实际验收时记录型号、固件、supported/enabled/reachable、已执行动作及证据，并按要求形成中英配对；研究档仅列待回答问题。IP-KVM 先记录是否存在必须看 BIOS/远程装机且现有 OOB 无法覆盖的案例。

**明确不做/延后：** 未实测机型不进入支持矩阵；不把研究候选当已支持；没有实需前不采购 IP-KVM、不开发 Guardian 适配。

### 28｜libvirt 绑定选型与生命周期

来源：`todo.md:123`，`docs/design/hypervisor-capabilities.md`，当前 `internal/agent/rpc/libvirt_provider.go`。

**推荐决策：保留 agent 驻宿主路线，先做只读真机/API 验收；下一片只考虑目标白名单内的启停。绑定选型先写比较结论，暂沿用现有 virsh 适配，不为尚未出现的需求立即替换。**

理由：

- **成本中**：已有只读 runner 和 RPC 基础可复用，立即换绑定会增加部署依赖与回归范围。
- **收益要分级**：列表/探测证明目标识别，启停证明最小写闭环；快照和克隆还引入存储格式、容量及一致性问题。
- **风险与权限相连**：当前 `virsh -r` 是只读边界，写操作需要独立权限、审计与确认，不能简单去掉 `-r`。
- **决策思路**：选型看接口覆盖、构建/运行依赖、取消能力和维护负担；如果必须换 Go 绑定，应由这些明确需求触发。

**立即执行动作：** 提供带本地 libvirt socket 的隔离宿主和测试 VM，先验默认 QEMU 与独立 LXC 连接及真实 HTTP→RPC 输出。然后比较现有 CLI 适配与 Go 绑定所需依赖、超时/错误语义；若维持 CLI，明确该阶段不引入新绑定，再单列启停设计及授权目标。PVE REST 测试不能代替本地 libvirt 验收。

**明确不做/延后：** Server 不直连宿主 libvirt；不一次做快照/克隆/迁移、不扩 Hyper-V/Firecracker；未核对存储条件前延后快照/克隆；目前名称数组不冒充 PVE 对象结构。

## 六、已完成审核中仍待实现拍板：补充 5 项

来源：`todo.md:241` 及其“表三 5 项能力仅评估”回执，细项见 `docs/review/luna-review-2026-10-18-response.md:67` 起。这里“已完成”指评估完成，不代表以下能力全部实现。与上面重复的部分只保留一个实施入口。

### 29｜Agent 准入与 secret 生命周期

**推荐决策：在已有默认拒绝和 enrollment 基础上补轮换/吊销设计，合并进入第 23/24 项；旧部署迁移必须先有保留入口。**

理由：

- **成本中**：既有准入不用重做，难点是轮换过程中不中断合法节点。
- **收益高**：凭据泄露或设备退出管理时，能明确停止其访问，而不必整体换所有节点秘密。
- **风险在迁移**：直接停用旧凭据可能让远端设备一起失联，失去修复入口。
- **决策思路**：秘密生命周期包括签发、使用、轮换、吊销和审计；“第一次能注册”只覆盖开头。

**立即执行动作：** 盘点现有节点和凭据关系、管理员预置需求及迁移路径，设计限时 enrollment、分批轮换和吊销后的连接处理；选一个可本地恢复的节点先验。

**明确不做/延后：** 不重新开放默认注册、不批量一刀切吊销；不另起与第 23/24 项重复的身份系统，本次不操作实际 secret。

### 30｜密码重置及验证码限速

**推荐决策：若相关入口对公网开放或邮件发送可用，建议优先做这一小项；与登录限流区分，独立完成忘记密码/重置/验证码的防滥用设计。**

理由：

- **成本低至中**：已有登录限流可借鉴，但不同入口需要不同计数和冷却规则。
- **收益高**：减少邮件轰炸、验证码猜测及发送额度损耗。
- **风险有双向性**：规则过松会被滥用，过严或按账号直接封禁又可能阻止正常用户找回。
- **决策思路**：既看攻击者能发多少请求，也看合法用户在共享 IP、失败或重试时能否完成恢复。

**立即执行动作：** 先核对 forgot/reset/verify-code 各入口暴露情况、邮件发送链和现有保护；为 IP、账号/邮箱设计有限窗口、发送冷却和统一响应，并验正常找回、限流及不泄露账号存在性。

**明确不做/延后：** 不把“登录已限流”当全部入口已保护；不默认加 CAPTCHA；当前单实例阶段不为此先上共享数据库，未来多实例再评估共享计数。

### 31｜持久化任务恢复与重试

**推荐决策：保留重启后遗留任务标失败的保守行为；并入第 23 项，先落任务身份、去重和人工重试审计，再对证明可重复的动作开放自动恢复。**

理由：

- **成本中至高**：需要协调任务存储、派发、目标执行和结果确认，而非启动时简单再发一次。
- **收益明确**：减少中断后的人工排查，同时避免任务永久悬挂。
- **风险最大的是重复副作用**：命令已执行但回复丢失时，重放可能重复创建、扣费或删除。
- **决策思路**：“至少一次”允许重复，“至多一次”可能漏做；需要按动作选择，并用去重证明安全，不能仅凭任务状态判断。

**立即执行动作：** 对只读查询、幂等状态设置、任意脚本分类；明确任务 ID、目标去重、租约/心跳和过期窗口，设计派发前后及结果丢失时的恢复规则，再安排故障注入验收。

**明确不做/延后：** 不自动重放所有 failed/pending 命令、不承诺任意脚本恰好执行一次；不另开与第 23 项重复的重试引擎。

### 32｜Agent/资源范围授权

**推荐决策：与第 24 项合并；多人共享或代管资源场景优先，否则保留设计结论，不提前建设完整多租户。**

理由：

- **成本中至高**：需要覆盖资源列表、详情、RPC、会话和动作 API，不能只改某一页。
- **收益与用户数相关**：同一管理员管自己的设备时收益有限，团队分权时直接影响数据与操作边界。
- **风险在旁路**：菜单隐藏后仍能直接请求 API，就没有形成有效隔离。
- **决策思路**：先确定资源属于谁，再验证“知道别人的资源 ID 也不能读或操作”。

**立即执行动作：** 先确认是否存在两位权限不同的使用者，建立资源归属和跨 API 授权矩阵；选择两组资源与两个账号验列表过滤、直接 ID 访问及 RPC/会话拒绝路径。

**明确不做/延后：** 不把角色/模块权限当资源隔离已完成；不另造第二套 RBAC；纯个人场景暂缓全面行隔离，但保留现有权限检查。

### 33｜Job 实时输出与进度

**推荐决策：维持 P2；当长任务的等待和排障确实妨碍使用时，再基于现有任务、终端传输能力设计。**

理由：

- **成本中至高**：要处理输出速度、缓冲、断线续接、权限和保留，并非持续刷新文本框。
- **收益有条件**：短任务最终输出已够用，长任务中途排障才有显著增益。
- **风险会放大**：无上限实时日志可能占满内存或暴露敏感输出，进度百分比也不能凭空计算。
- **决策思路**：先明确用户中途需要知道什么，是运行中、最近日志，还是可信的完成比例，再选最小方案。

**立即执行动作：** 收集一条真实长任务、等待时长和所需中途信息；将输出上限、慢消费者处理、断线恢复及权限列为验收条件，评估复用既有通道的方案。

**明确不做/延后：** 不新增第二套任意命令执行通道、不无限保留日志、不把 Job 输出需求扩大成已明确不做的 workflow SSE；无真实场景前不实现。

### 已执行盘点明细（本仓只读核对，未调用任何外部凭据）

**盘点 20（P0 云接线）：** `internal/server/api_cloud.go` 注册的实例路由为只读数据库台账（`handleCloudInstances`，`api_cloud.go:121`），不调用厂商发现 API；账号路由仅账号 CRUD 与 secret 写入（`handleCloudAccounts:165`、`handleCloudAccount:227`）。厂商侧 `internal/cloud/provider.go:19-24` 已定义 `Create/Start/Stop/Delete` 与 `GetOperation` 接口，`aliyun.go:241/295` 与 `tencent.go:258/326` 均已实现 Create/Start/Stop/Delete。**仍缺的接线**：① 实例发现——server 未接厂商 `ListInstances` 全量同步，只读台账不自动发现；② 生命周期——server 未暴露 create/start/stop/delete HTTP 路由，`operation.go` 仅被 provider 内部消费；③ 界面——`web/src/pages/` 无 cloud/instance/provider 页面，`web/src/api/` 无对应客户端封装。结论：厂商适配器与接口契约齐备，缺口在 server 路由接线与 UI。

**盘点 23（capability 上报与消费）：** 上报源＝注册负载 `RegisterPayload.Capabilities`（`protocol/message.go:84`，字段 `Type/Endpoint/Version/Metadata`，`message.go:56-63`）、探针注册 `probeagent/upstream.go:247`；落库经 `inventory/sync.go:105-111` 与 `storage/capability_crypto.go`（Config 加密序列化）。消费位置＝`server/api_stacks.go:223/230/524`（`HasCapability("docker-api"/"docker")`）、`api_overlay_cloud.go:209-232`（从 capability metadata 提取 zerotier nodeId/deviceId）、`server/api.go:769-784`（web/mobile 读 `cap.type/cap.metadata`）、`server/server.go:540-561`（对齐 storage.Capability）。**契约缺口**：capability 目前无独立「权限状态」（readonly/writable）字段，消费方靠 `HasCapability(type)` 硬编码类型判断，版本/权限状态未进入能力模型；`version` 字段已存在但无契约约束。

**盘点 25（WoL/PVE/云电源接口）：** WoL＝`internal/oob/wol/wol.go`（`MagicPacket:24`、`ParseMAC:41`、`SubnetBroadcast:66`、`Sender.Send:113`，UDP 广播，发送注入点）。PVE＝`internal/pve/client.go`（`StartVM:287`、`StopVM:300`、`RestartVM:313`、`SuspendVM:326`，经 `/api2/json/.../status/{start,stop,reboot}`）。云电源＝`internal/cloud/provider.go:23-24`（`StartInstance/StopInstance`），aliyun `aliyun.go:295`、tencent `tencent.go:326` 实现。三者均为独立接口，无统一电源抽象；结论：不重写电源 provider，归并已有能力即可。

**盘点 28（libvirt CLI vs Go 绑定）：** 现状＝`internal/agent/rpc/libvirt_provider.go` 用 `virsh -r` 只读连接（`libvirtRun` 注入点），`LibvirtAvailable:64` 走 `exec.LookPath`，超时 `libvirtProbeTimeout=5s`/`libvirtListTimeout=10s`；仅 `capabilities/vms.list/containers.list` 三动作，未知动作 fail-closed。**依赖对比**：当前 go.mod/go.sum 无任何 libvirt Go 绑定（`grep -i libvirt go.mod go.sum`＝0），保持 CLI 适配则零新增依赖；引入 Go 绑定（如 libvirt-go）需新增 cgo＋系统 libvirt-dev 构建依赖与版本耦合。结论：暂沿用 virsh 适配符合「不立即替换」的推荐，绑定选型比较结论已成立。

**盘点 31（任务类型分类）：** 现有 job 仅 `exec` 与 `cancel` 两动作（`job_provider.go:35-36`），`exec` 经 `sh -c` 执行任意命令（`job_provider_unix.go:17`），有超时/长度/输出上限（`jobExecMaxTimeout=300s`、`jobExecMaxCommand=16KB`、`jobExecMaxOutput=64KB`，`job_provider.go:45-50`）。**分类结论**：只读查询（如 `vms.list`、`containers.list`、系统探测）与幂等状态设置（如 status 置位）已有独立、可安全自动重试的语义；任意脚本（`job.exec` 的 `sh -c`）默认不自动重试，需先落任务身份/去重再评估。恢复逻辑未见（重启后遗留任务行为在别处判定）。
