# 资源级权限矩阵与短期凭据设计（项 24＋32 合并）

> 依据：决策项 24（P0 短期凭据、资源级权限与轻量模式——拆开排期）与项 32（Agent/资源范围授权——与 24 合并）。
> 状态：**设计稿**。实现待用户明确「个人/团队使用方式」并确认存在第二位权限不同使用者后单独立项。
> 边界：不另造完整证书基础设施、不因短期 token 省略资源检查、不先分叉两套 agent、不另造第二套 RBAC、不把角色/模块权限当资源隔离已完成（决策明确不做）。

## 1. 问题与目标

- 当前 `Agent.HasCapability(type)` 按**类型**门控（`agent.go:129`），`api_stacks.go` 等按 capability 类型放行动作——**没有按资源 ID 隔离**。知道资源 ID 即可读/操作，菜单隐藏不等于 API 拒绝（决策项 32 风险：旁路）。
- **目标**：先画「角色×资源×动作」矩阵，选最敏感一类动作试点；证明「知道别人的资源 ID 也不能读或操作」。
- **触发**：多人共享/代管资源场景优先；纯个人场景保留设计结论、不提前建设完整多租户（决策项 32）。

## 2. 角色×资源×动作矩阵（建议）

| 角色 | 可读资源范围 | 可写动作 | 说明 |
|---|---|---|---|
| `owner` | 自有资源 | 全部（含销毁） | 资源归属者 |
| `operator` | 自有＋被授权资源 | 启停/重启（无销毁） | 日常运维 |
| `viewer` | 自有＋被授权资源 | 无 | 只读 |
| `admin` | 全部 | 全部 | 保留给系统/审计；不默认授予 |

- **资源维度**：按「资源 ID → 归属 owner」建立归属表；越权判断 = `(user, resource, action)` 查矩阵，而非仅 capability 类型。
- **跨 API 一致性**：列表过滤、详情、RPC、会话、动作 API 走同一授权函数；仅隐藏菜单不算授权（决策项 32「菜单隐藏后仍能直接请求 API 就没有形成有效隔离」）。

## 3. 短期凭据与资源级限制

- **凭据**：短期 token 不自动限制可操作资源（决策项 24「token 有效期短，并不自动限制可操作资源」）——资源级检查必须独立做，不因短期 token 省略。
- **过期/撤销**：列已有长期凭据迁移规则；撤销/过期路径先落，避免凭据残留（决策项 24「多人访问时优先资源级限制+凭据撤销/过期」）。
- **试点动作**：选最敏感一类（如 `instance.delete` 或 `virt.vm.*`）先做资源级限制，其余后续扩。

## 4. 轻量模式（拆开排期，不在本片）

- 轻量模式是**独立目标**（内存/CPU/磁盘/恢复行为），与权限矩阵拆开排期（决策项 24「拆开排期」）。
- 需为 OpenWrt 等目标给出资源预算并采集基线——**采集需目标设备**，本次标记待用户，不臆测测量结果。

## 5. 待用户确认项

- **个人/团队使用方式**：决定 `owner/operator/viewer` 是否简化成「自有/共享」二档（决策项 24「明确个人/团队使用方式」）。
- **两位权限不同使用者**：确认存在，才能验「知道别人资源 ID 也不能读/操作」（决策项 32）。
- **OpenWrt 资源预算基线**：需目标设备实测，据测量结果选是否需要最小构建（决策项 24）。

## 6. 决策对照

本设计落实项 24 的「画角色×资源×动作矩阵、选最敏感一类试点、列过期/撤销与迁移规则」与项 32 的「建立资源归属和跨 API 授权矩阵、验证直接 ID 访问及 RPC/会话拒绝路径」；实现与验证均待用户确认场景后推进。不另造第二套 RBAC、不把角色权限当资源隔离已完成。
