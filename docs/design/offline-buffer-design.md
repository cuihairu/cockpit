# 离线缓冲与电源接口归并设计（项 25）

> 依据：决策项 25（不整包立项；P0 后按实际断线损失优先评估离线缓冲，其余按需求触发，统一电源只做已有能力归并）。
> 状态：**设计稿**。缓冲容量/过期/去重/补报顺序为本设计内容；断线时长数据与双人协作场景需实际数据（待用户）；电源接口盘点见 §4（已核实，不重写）。
> 边界：不一口气做四套研究报告、不重写电源 provider、不缓存离线任意写命令并在重连后自动执行（决策明确不做）。

## 1. 离线缓冲（数据可靠性，优先级高）

- **问题**：agent 断线期间产生的监测数据/事件会丢失；重连后补报需避免重复与乱序。
- **容量**：有限队列（建议按条数+字节双上限，如 1000 条 / 64MB）；超限丢最旧并记丢弃计数（不静默丢弃）。
- **过期**：补报窗口（如 24h）；超窗数据不补报、仅计数（避免重连后突发大量陈旧数据）。
- **去重**：每条带稳定 ID（事件 ID / 时间戳+序号）；重连补报按 ID 去重，server 幂等接收。
- **补报顺序**：按时间升序补报；失败重试 N 次后停（不无限重试），保留本地待人工。
- **只用于幂等/只读数据**：不缓存任意写命令并在重连后自动执行（决策边界）——写命令离线时丢弃并告警，不做「恰好一次」承诺。

## 2. 会话共享（多人协作，按需求触发）

- **触发**：双人远程协作需求出现才立项；本次只记录边界（只看/可操作）。
- **设计要点**（触发后）：共享会话的操作归属（谁执行）、秘密暴露边界、并发操作裁决。

## 3. 源码深读（研究，不整包）

- 只选择当前设计问题对应的项目与章节（决策项 25「源码阅读只选择当前设计问题对应的项目和章节」），不一口气做四套研究报告。

## 4. 电源接口盘点（已核实，归并不重写）

| 接口 | 位置 | 能力 |
|---|---|---|
| WoL | `internal/oob/wol/wol.go:24/113` | `MagicPacket`、`ParseMAC`、`SubnetBroadcast`、`Sender.Send`（UDP 广播，发送注入点） |
| PVE 电源 | `internal/pve/client.go:287-326` | `StartVM`/`StopVM`/`RestartVM`/`SuspendVM`（`/api2/json/.../status/{start,stop,reboot}`） |
| 云电源 | `internal/cloud/provider.go:23-24` | `StartInstance`/`StopInstance`（aliyun `aliyun.go:295`、tencent `tencent.go:326`） |

- **结论**：三者均已有独立实现，无统一电源抽象；**归并**＝统一入口/类型收敛，不重写 provider（决策「统一电源只做已有能力的归并」）。
